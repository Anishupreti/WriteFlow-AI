## 0.16.1 — Context association bugfix

- Fixed `ContextDOM.associated()`: it only succeeded when the comment field was a literal DOM descendant of the post, or inside a `[role="dialog"]` with exactly one candidate. Neither matches how Reddit, Facebook, LinkedIn, etc. actually render (the comment box sits as a sibling near the post, not nested inside it), so context extraction returned null almost everywhere in real use despite passing all fixture tests.
- Root cause of the test/reality gap: every fixture in `tests/fixtures.cjs` places the field literally inside the post tag, which was the one layout that already worked. No fixture tested the sibling-layout case.
- Fix generalizes the old dialog-only fallback: walk up from the field, and at each ancestor scope check for exactly one visible post candidate; stop and return null (never guess) if a scope contains more than one. This does not reintroduce the earlier "wrong comment" issue — verified against a same-scope-two-posts case, which still correctly returns null.
- Verified via jsdom (with getClientRects/isContentEditable polyfills, since jsdom doesn't implement real layout) against three cases: normal top-level post, ambiguous multi-post scope, and a Facebook-style layout with an existing comment nearby. Live-browser/Playwright verification was not possible in this environment (no network access to Playwright's browser-download CDN) — recommend running the existing `npm test` suite locally to confirm.

## 0.16.7 — Milestone 4, Batch 2: Style DNA (learn from accepted edits)

- New `services/style-learning.js`: pure text-comparison functions (no chrome API, no side effects) that compare a WriteFlow-generated suggestion to what the person actually left it as, and derive small directional signals — shorter/longer, more/fewer contractions, corporate jargon removed, greeting/sign-off added or removed, more/fewer emoji.
- `services/storage.js`: added `recordStyleEdit(before, after)`, gated entirely behind the `styleDNALearningEnabled` opt-in from Batch 1 (default off — this function is a no-op unless explicitly turned on). Applies small, deliberate nudges (±0.08 per signal) to the numeric styleDNA fields, derives the three categorical fields (sentenceLength, greetingStyle, signoffStyle) from the relevant numeric direction, and increments `styleDNASamples`. Also added `resetStyleDNA()`.
- Privacy/safety by construction, not by an added check: `before` is always literally the text WriteFlow generated and the person accepted (Replace/Insert) — there is no code path that feeds it arbitrary page content. Sensitive fields (passwords, payment forms) were already excluded from WriteFlow's reach entirely (content/detector.js), so they're excluded from learning too, automatically.
- `content/ui.js`: the Replace/Insert handlers now record what was actually inserted per-field in a `WeakMap` (auto-cleared if the field is removed from the DOM, so this can't leak memory on long-lived SPA pages). New `checkFieldEdit(field)`, called from `content/index.js`'s blur handler for every blurred field — cheap no-op for the vast majority that were never given a suggestion; for the rare field that was, compares current text to what was inserted and calls `recordStyleEdit`.
- Verified via jsdom: signal computation across five realistic before/after pairs (shortened+contractions, greeting/signoff removed, corporate jargon removed, identical text → null, empty text → null); the opt-in gate (off → no state change at all; on → correct nudges applied and sample count incremented); `resetStyleDNA` correctly restores neutral defaults. Found and fixed a real gap during testing: the signoff regex didn't handle the extremely common "Best, Sam" pattern (a name after the signoff word) — fixed and reverified, including a guard case to confirm the looser pattern doesn't fire on near-identical text with no real signoff change.
- As in prior batches: the blur-wiring itself (content/index.js → UI.checkFieldEdit) is syntax-valid and carefully reasoned through (confirmed detector.js's onBlur passes the same resolved element reference used as the WeakMap key), but not exercised end-to-end due to the same vm+jsdom addEventListener limitation noted in Milestone 3. All the actual learning logic (the part with real risk of getting wrong) is what's verified above.

## 0.17.3 — Milestone 6, Batch 3a: multi-level comment threads for social platforms

- `content/platform-adapters.js`'s `extract()` now walks the FULL ancestor chain of nested comments for comment-based platforms (LinkedIn, Twitter, Reddit, Facebook, YouTube, Instagram, TikTok, Quora, Substack) instead of stopping at one parent level — a reply three or four levels deep into a thread now gets real conversation context, not just the comment directly above it. Capped at 5 ancestor levels to bound extraction cost and prompt size on deeply-nested threads (matches the 6-message cap already used for email/chat platforms).
- Found and fixed a real ordering bug during testing, before it shipped: the first version split the nearest ancestor into the existing `parentText` field and put everything further back into `conversation`, but `ContextModel.serialize()` always renders `parentText` BEFORE the conversation array — so the most recent ancestor appeared ahead of genuinely older ones in the serialized prompt text, backwards from actual chronological order. Fixed: when there's any ancestor comment at all, the whole chain now goes into `conversation` (oldest-first); `parentText` only falls back to the post itself when there's no ancestor comment to walk to at all. Verified this produces correct oldest-to-newest ordering in the actual serialized text sent to the model, not just correct data shape.
- Updated the `conversationContext` capability flag (declared per-platform, not yet consumed by any code, but kept accurate) to reflect that comment-based platforms can now genuinely provide multi-level conversation data too, not just message-based ones (email/chat).
- Verified via jsdom against three cases: a 4-level nested thread (correct primaryText/conversation, correct chronological order in the serialized output); a normal 2-level thread with no real ancestor (parentText falls back to the post, conversation stays empty — no behavior change from before this batch); a 7-level thread confirming the depth-5 cap actually bounds extraction (4 conversation entries, not 6).
- Scope note: this only affects comment-based platforms with DOM-nested reply structure (nested comment elements literally containing their replies), which is the common pattern for Reddit/Facebook/LinkedIn/Twitter-style threads. A platform that renders nested replies via a flat list with indentation styling instead of real DOM nesting would not benefit from this without separate work — not verified against any live platform's current real markup (same "best-effort" caveat as the rest of this fork's extractors).

## 0.17.4 — Milestone 7, Batch 1: Dynamic Adjustment Chips

- Replaced the static, always-identical 3-chip row ("Shorter", "More formal", "Different angle" -- shown for every single suggestion regardless of content) with a full 13-option catalog from the spec and a local, rule-based selector that picks 3-5 chips per suggestion based on the actual generated text and the generation mode.
- Heuristics are cheap and synchronous -- no extra AI call to decide which chips to show, consistent with this project's existing cost-control principle (an automatic AI request just to choose adjustment buttons would be a wasteful trade for something a few regexes can do locally):
  - Word count >=40 -> offers "Shorter"; a non-trivial but not-huge suggestion offers "Make punchier" instead (never both -- one length-related chip at a time)
  - Emoji present -> offers "Remove emojis"; absent -> chip omitted entirely (nothing to remove)
  - No question mark, and the mode is comment/email/write-for-me -> offers "Ask a question"; already has one -> omitted
  - Mode-flavored tone chips: email leans "More professional" + "Warmer"; comment leans "More casual" + "Warmer"; plain rewrite leans "Sound more natural"
  - "Different angle" always included as a safe universal fallback
  - A fixed-priority fallback pool tops up to at least 3 chips if the above under-selects for a given case
- "Sound like me" is in the catalog but deliberately never auto-selected yet -- it needs an async Style DNA lookup that `renderSuggestion` doesn't currently have (Batch 2). "Add humour" is also in the catalog but deliberately excluded from auto-selection -- appropriateness is too context-dependent to guess safely with a cheap local heuristic.
- Verified via isolated logic tests (the selector needs no DOM, so tested directly rather than fighting this project's known vm+jsdom UI-loading unreliability): a long email reply, a short comment with an emoji, a comment that already ends in a question, a plain rewrite, and a write-for-me draft all produced correctly different, contextually-fitting chip sets; confirmed the count is always 3-5, never duplicates, and neither deferred chip (sound_like_me, add_humour) is ever auto-selected.
- Replace / Insert / Copy / Undo (and the separate Regenerate button) are all untouched -- this batch only replaced the adjustment-chip markup and its selection logic, nothing else in the suggestion panel.
